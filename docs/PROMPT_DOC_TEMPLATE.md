# Промпт: привести документ раздела к единому шаблону

Как пользоваться: откройте новый чат в проекте, подключите репозиторий `makutaII/ec-project`, вставьте текст из блока «Промпт» ниже и в первой строке укажите раздел, например `Раздел: ATTN_16_mechanisms.md`. Образцы готового результата: [ATTN_12_switches.md](ATTN_12_switches.md) (эталон), [ATTN_25_rooms.md](../ATTN_25_rooms.md), [ATTN_14_observe_room.md](../ATTN_14_observe_room.md).

Зачем шаблон: убрать мусор, сократить объём, разложить документ по одинаковым разделам. Позже из каждого документа будут выделены руководства для трёх аудиторий: разработчика, ИИ-ассистента и пользователя проекта (игрока и автора). Поэтому каждый документ обязан содержать три блока инструкций и одинаковые заголовки.

## Промпт

```
Раздел: <имя файла документа, например ATTN_16_mechanisms.md>

Задача: переписать документ раздела по единому шаблону проекта. Образец: docs/ATTN_12_switches.md.
Ориентир по результату: ATTN_25_rooms.md и ATTN_14_observe_room.md. Прочитай образец и один из ориентиров
целиком до начала работы, затем прочитай переписываемый документ целиком.

Цель переписывания:
- убрать мусор: историю разработки, этапы, которые уже сделаны, аудиты, журналы «что сделали в патче»,
  дубли, отвергнутые варианты, вопросы, на которые ответ уже дан;
- сократить объём без потери фактов, нужных для работы с готовым продуктом;
- разложить текст по разделам шаблона;
- дать три набора инструкций: для разработчика, для ИИ-ассистента, для пользователя проекта.
Позже из каждого документа выделят руководства для этих трёх аудиторий, поэтому границы блоков должны быть чёткими.

Что остаётся в документе: принципы, описание устройства и данных, правила, таблицы (поля, роли, лимиты,
сообщения), инструкции «как сделать», отладка и проверка, хоткеи, ограничения. Всё, что нужно для
дальнейшей работы с созданным продуктом.

Что уходит: сами этапы процесса разработки (S0, RM0, T1 и т.п.) с галочками «сделано», описания «что сделано
в патче», аудиты и таблицы расхождений, обоснования выбора между вариантами (решение остаётся одной строкой
в принципах), историю замеров, которая не нужна для текущей работы.

Не сделанные этапы не трогаем: этап, у которого все пункты не выполнены, остаётся в документе в исходном виде
в разделе «Не начатые этапы». Частично сделанный этап разбирается: сделанное описывается как свойство
продукта, несделанные пункты уходят в «Замечания и доработки».

Структура документа (номер раздела N берётся из имени файла, нумерация подразделов N.1, N.2, ...):

1. Заголовок «# ATTN N. Название **[статус]**», статус одним из: [решено], [решено, кроме §N.x], [предложение].
2. Строка «Продолжение ...», строка «Связанные разделы» со ссылками на соседние документы.
3. «Оглавление» ссылками на все разделы (якоря в стиле GitHub: #141-назначение-и-состав).
4. N.1 «Назначение и состав»: что описывает раздел, таблица объектов или комнат, таблица «Основные файлы»
   (файл, что делает).
5. N.2 «Принципы» (или «Принципы и модель данных»): список принципов; подраздел «Инварианты, которые нельзя
   ломать»; принятые решения автора одной строкой каждое; модель данных и поля паспортов таблицами.
6. Разделы по объектам раздела (устройство, поведение, данные). Нумерация сквозная. Якоря важных разделов,
   на которые есть ссылки из других документов и из комментариев в коде, не переименовывай и не удаляй.
7. «Инструкции» с тремя подразделами, всегда с такими заголовками:
   - «### Для разработчика»: нумерованные «как сделать» (добавить объект, поле, правило, команду), список
     «Не нарушать при правках»;
   - «### Для ИИ-ассистента»: что прочитать перед правкой, какие правила обязательны, чего не делать, как
     оформлять результат (проверки для редактора, патч), какие данные брать только из инструментов;
   - «### Для пользователя проекта»: что делает игрок и что делает автор или админ, простыми словами, без имён
     внутренних классов там, где можно обойтись.
8. «Отладка и проверка»: тесты и как их запускать (таблица «тест, что проверяет»), отладочные вкладки и
   клавиши, таблица «сообщение или признак, причина», список «что проверить в редакторе после правки».
9. «Хоткеи» (если они есть у раздела; иначе внести в «Отладка и проверка»).
10. «Ограничения и допущения»: что не поддерживается, на что опирается раздел, что проверено только по коду.
11. «Замечания и доработки»: «### Недоделки раздела» со списком `- [ ]` и `- [x]`, сгруппированным заголовками
    жирным шрифтом; «### Замечания по тестам». Сюда попадают все недоделки, найденные в переписываемом тексте:
    открытые вопросы автору, невыполненные проверки, замеры, которые автор не сделал, техдолг, хвосты
    («удалить потом», «перенести позже»), расхождения с другими документами. Каждый пункт одной строкой,
    с указанием файла или раздела.

Правила переписывания:
- Не выдумывай фактов. Если сомневаешься, проверь по коду репозитория (Grep, Read) или оставь пометку
  «не подтверждено» в «Замечаниях и доработках».
- Не меняй смысл решений автора. Записи автора имеют приоритет над остальным текстом.
- Не трогай документ раздела, который не назван в задаче. Документ с префиксом 0_ (например, пайплайн
  моделей) не переписывай без отдельного указания.
- Ссылки и якоря: после правки проверь, что все ссылки на другие документы и внутри документа ведут
  в существующий файл и заголовок. Найди ссылки на твой документ из других файлов
  (grep по имени файла и по «§N.») и исправь те, что стали неверными; если якорь в коде (комментарии .gd, .py),
  код не правь, а сохрани номер раздела.
- Код, сцены и ресурсы не меняются: переписывается только документация (и ссылки в других документах).
- Форматирование: русский язык, короткие предложения, таблицы там, где сравнивают или перечисляют поля,
  без длинных тире, без эмодзи, без воды. Имена файлов, полей и клавиш в обратных кавычках.
- Если часть документа к другой аудитории ещё не определилась, помести её в раздел по смыслу и добавь
  пометку в «Замечания и доработки».

Проверки перед выдачей:
1. Все разделы шаблона на месте, оглавление совпадает с заголовками.
2. Скрипт проверки ссылок и якорей не находит битых.
3. Каждая недоделка из исходного текста либо описана в «Замечаниях и доработках», либо явно решена.
4. Не осталось строк вида «этап N», «сделано в патче», «RM», «S0», «план шагов» вне раздела «Не начатые этапы».

Выдача: по правилам проекта (инструкции проекта о формате патчей): git format-patch -1 --binary, проверка
git am -3 на чистом клоне, имя файла 0001-<english-name>.patch, Godot не запускать. В ответе коротко: что
осталось в документе, что вынесено в «Замечания и доработки» (число пунктов), какие ссылки в других файлах
исправлены, какие допущения сделаны.
```

## Что менять в промпте под конкретный раздел

- Если у раздела есть этапы, часть которых не начата, добавьте в первую строку: `Не начатые этапы: <перечень>`. Они остаются в исходном виде.
- Если раздел ведёт несколько объектов (как ATTN_12), оставьте по одному подразделу на объект, а «Принципы», «Паспорта», «Инструкции», «Проверка» делайте общими.
- Если у раздела нет игрока-пользователя (внутренний инструмент), в блоке «Для пользователя проекта» опишите автора или админа, а игрока опустите с пометкой «игрок не взаимодействует».

## Шаблон заголовков (копировать в начало нового документа)

```
# ATTN N. Название **[статус]**

Продолжение [TDD.md](../ATTN_TDD.md). Связанные разделы: ...

## Оглавление
## N.1. Назначение и состав        (+ ### Основные файлы)
## N.2. Принципы                   (+ ### Инварианты, которые нельзя ломать, ### Решения)
## N.3 ... N.k. Разделы по объектам
## N.k+1. Инструкции               (### Для разработчика / Для ИИ-ассистента / Для пользователя проекта)
## N.k+2. Отладка и проверка
## N.k+3. Хоткеи
## N.k+4. Ограничения и допущения
## N.k+5. Замечания и доработки    (### Недоделки раздела / ### Замечания по тестам)
```
