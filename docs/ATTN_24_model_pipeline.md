## 24.1. Назначение и состав

Цепочка: **Blender (`.blend`) -> `.glb` -> Godot (сцена-обёртка + паспорт)**. Модель в Blender задаёт геометрию, нулевую точку, шарниры подвижных частей, материалы, UV и числа движения. Паспорт в Godot (`WagonConfig`, `MechanismConfig`, `LightConfig`) хранит всё, что работает в игре: состояния, команды, сохранение, правила света.

| Что | Где | Назначение |
|---|---|---|
| Скрипт Blender | `tools/blender/ec_model_tools.py` | панель EC: проверка до экспорта, роли, подготовка, UV, эталон, ключи механизма, экспорт |
| Шпаргалка | `tools/blender/CHEATSHEET.md` | пошаговый порядок работы в Blender с кнопками панели |
| Проверка файла | `tools/glb_preflight.py` | читает готовый `.glb` или `.gltf` без Godot, печатает ошибки и заготовки чисел для конфигов |
| Модели игры | `data/models/<id>/` | `.glb`, `.glb.import`, сцена-обёртка `.tscn` |
| Объекты каталога | `data/<категория>/objects/<id>.tres` | как раньше (каталог читает только эти папки) |
| Паспорт | `data/library/info/<ключ>.tres` | как раньше |
| Тесты | `tests/mech_anim_test.tscn`, `tests/library_paint_test.tscn` | механизмы `ANIM` (12 проверок) и покраска, включая `paint_*` |

Рабочие папки автора: исходники `.blend` в `E:\GodotCopy\Blender\Art\`, экспорт в `D:\Godot\ec-project\data\models\<id>\<id>.glb` (поле «Папка моделей» панели EC).

## 24.2. Принципы

1. **Масштаб.** 1 единица Blender = 1 м прототипа = 1 единица игры (длина кузова равна `2 × coupler_offset`). Unit System Metric, Unit Scale 1.0. Комнатные предметы делаются иначе (реальный предмет умножается на 100, [ATTN_25](ATTN_25_rooms.md)).
2. **Оси.** Нос модели смотрит в **+Y Blender**, верх это +Z, правый борт по ходу +X. Экспортёр glTF при включённом «+Y Up» переводит `(x, y, z)` в `(x, z, -y)`, поэтому +Y Blender становится **-Z Godot** (нос проекта).
3. **Нулевая точка: ось буферов.** Центр кузова по X и Y в нуле, **Z=0 это ось буферов**. Все вагоны стоят буферами на одной высоте над рельсом: по **NEM 303 «Puffer»** (обязательная норма, издание 2015, табл. 1) для H0 высота середины буфера 12.2 ±0.5 мм, расстояние между осями 20.0 ±0.2 мм, нижняя кромка тарелки не ниже 9.6 мм. В единицах игры (1:87): **1.061 ±0.043**, **1.74**, **0.835**. У новых моделей `offset_mesh_y = WagonConfig.BUFFER_HEIGHT` (1.061), головка рельса в Blender на Z = −1.061. Диаметр колеса на высоту кузова не влияет: тележка встаёт на рельс сама (`wheel_pair_position.y` это радиус), колесо слишком большого диаметра в вырезы кузова не влезет (ограничение модели, видно по эталону).
4. **Кузов это корень.** Один корневой объект с `role = body`, все подвижные части и пустышки его дети. Колёса, тележки, коллизия, источники света, камеры и отладочные узлы в файл не входят.
5. **Один подвижный элемент это один объект** со своей ролью. Origin подвижной части стоит на оси вращения (для сдвига положение любое, но одинаковое у парных частей).
6. **Источник истины для движения и света это паспорт в Godot** (`MechanismConfig`, `LightConfig`: состояния, сохранение, команды, правила). Blender даёт геометрию, origin и **числа**: действие `mech_<id>` превращается в заготовку конфига (или ведёт механизм `ANIM` напрямую), пустышки-якоря дают координаты света.
7. **Красимое отмечено префиксом материала `paint_`.** Свет и тени в цвет красимых материалов не запекаются.
8. **Мешей в сцене нет.** Сцена-обёртка только инстансит `.glb`: повторный экспорт обновляет модель сам, настройки импорта (UV2) действуют, `.tscn` весит килобайты.
9. **Старое не ломаем.** Старые модели, сцены и паспорта остаются на местах; новые идут в `data/models/<id>/`.

## 24.3. Контракт: что код ждёт от модели

Из этого выведены правила раздела. Поведение проверено по коду.

1. **Роль узла.** `PartRegistry` (`setting/part_registry.gd`) берёт роль из меты `role` или из `extras.role`. Godot кладёт Custom Property **объекта** Blender в мету `extras` узла. Явная роль сильнее имени узла: если хоть у одного узла есть мета-роль, имена не рассматриваются. Роль на данных меша Godot в узел не переносит, игра её не увидит.
2. **Кузов это первый меш.** `C_Visual` собирает `mesh_nodes` обходом в глубину; `C_TrainVisual` делает `mesh_nodes[0].position.y = offset_mesh_y` и сдвигает коллизию кузова на ту же величину. Кузов (`role=body`) это первый `MeshInstance3D` в порядке обхода, подвижные части его дети и поднимаются вместе с ним. Высота кузова в Blender **перезаписывается** паспортом: `offset_mesh_y` это абсолютная высота начала кузова над головкой рельса (корень вагона лежит на уровне головки рельса).
3. **Механизм двигает узел вокруг его origin.** `SLIDE`: `rest.origin + axis * travel * smoothstep(t)`; `ROTATE`: `rest.basis * Basis(axis, угол)` с центром в origin узла. `rest` запоминается один раз при создании сущности. Ось задана в локальных осях **родителя** узла (у частей кузова это оси кузова).
4. **Свет это числа в конфиге, не узлы.** `LightConfig` хранит `position` и `rotation_deg` в системе корня сцены модели, родитель задаётся ролью (`anchor_role`).
5. **Покраска.** `VariantApplier.apply(mesh_nodes, ...)` красит все переданные меши, кроме тележек и колёс (они строятся позже из своих сцен). Id зоны это `<имя узла>#<номер поверхности>` либо `all`. Зона `all` пропускает прозрачные материалы; если у модели есть хоть один материал `paint_*`, красит **только** их. Кроющая краска обнуляет `albedo_texture` и цвет вершин, при отделке, отличной от `keep`, ещё и карты шероховатости и металличности; `ao_texture` и нормали остаются.
6. **Кисть** строится на одном целевом меше (`PaintEngine.pick_target`, меш кузова с UV2).
7. **Тележки и колёса** приходят из `bogie_*.tscn` и `wheel_pair_*.tscn` через `BogieConfig`.
8. **Коллизия кузова** (`WagonCollisionShape3D`) лежит в сцене как `BoxShape3D`, подгоняется вручную по числам отчёта (позиция до подъёма на `offset_mesh_y`).
9. **Слой коллизии вагона** задаёт `C_TrainVisual` (`on_select_layer`: слой `trains`, у выбранного `ghost`, маска как у остальных вагонов), слой и маска из сцены игнорируются. У сцены-обёртки без явного слоя стоит слой по умолчанию 1 (земля); луч курсора (`get_mouse_ray`) отбрасывает боковые грани слоя земли, и ховер вагона был бы только по крыше.

## 24.4. Именование

**Роли** (Custom Property `role`, строка, на **объекте**; только `a-z`, `0-9`, `_`):

| Что | Роль | Примечание |
|---|---|---|
| Кузов | `body` | ровно один, корень |
| Дверь, люк | `door_l`, `door_r`, `hatch_1` | пары через `_l/_r` или `_1/_2` |
| Пантограф | `pantograph_1`, `pantograph_arm_1` | |
| Дышла, шатуны | `rod_main_l`, `rod_side_l` | |
| Вентилятор, маяк | `fan_1`, `beacon_1` | вращение вокруг origin |
| Ось буфера | `buffer_1`...`buffer_4` | пустышка на оси (или меш буфера); по ним проверяется высота, шаг и нижняя кромка |
| Якорь света | `headlight_front` (белая передняя), `headlight_rear` (красная задняя), `cab_light`, `anchor_window_1` | пустышка, только для чтения чисел; имена как `LightConfig.id`, цвет задаётся в `LightConfig`; допустимы и `light_*` |
| Деталь на замену | `part_<слот>` | заготовка для [ATTN_22](ATTN_22_library.md) L5 |

**Материалы:**

| Префикс | Назначение | В игре |
|---|---|---|
| `paint_` | красится (кузов, крыша, полосы) | зона покраски; «Весь корпус» красит только их, если они есть |
| `trim_` | отделка (рамы окон, ручки) | не красится |
| `metal_`, `rubber_` | сталь, резина | не красится |
| `glass_` | стекло | `alphaMode` BLEND, зона `all` его не трогает |
| `emit_` | светящееся | основа для `glow_*` в `LightConfig` |

**Анимации:** `mech_<id>`, где `<id>` это `MechanismConfig.id` (в паспорте имя анимации задаёт `anim_name`, по умолчанию `mech_<id>`). Узлы и материалы без хвоста `.001` и без пробелов, не `Cube`, `Plane`, `Empty`: id зоны покраски стоит на имени узла.

## 24.5. Покраска, материалы, UV

* **Материалы:** только Principled BSDF (совместим с glTF), один материал на зону покраски. Красимые поверхности `paint_*`, у них цвет плоский.
* **Запекание.** Свет и тени в цвет `paint_*` не запекаются (кроющая краска выбрасывает `albedo_texture`). AO идёт отдельной картой (канал R карты ORM или отдельный Occlusion): `ao_texture` покраска не трогает. Некрасимые материалы можно запекать целиком. Текстуры 1024 или 2048, вшиваются в `.glb`.
* **UV.** Первая карта (`UV1`, в glTF `TEXCOORD_0`) для текстур, **вторая** (`UV2`, `TEXCOORD_1`) без перекрытий для кисти и AO. Игра использует две карты, glTF экспортирует все: лишние убираются. Кнопка «Создать UV1/UV2» доводит число карт до двух (Smart UV Project и Lightmap Pack, существующие карты не трогает). Без UV2 кисть недоступна, покраска по зонам работает; Godot умеет создать UV2 при импорте (Advanced Import Settings, Meshes, Light Baking = Static Lightmaps).
* **Бюджет:** до 40 000 треугольников у вагона, 60 000 у локомотива (проверяет скрипт).

## 24.6. Механизмы

Состояние 0..1 хранит `C_Mechanisms`; число и тип движения берутся так:

| Случай | Как |
|---|---|
| Простое движение (`SLIDE`, `ROTATE`) | в Blender действие `mech_<id>`; `glb_preflight.py` печатает заготовку `MechanismConfig` (роль, `actuator`, `axis`, `travel`, `duration`); числа переносятся в `.tres` |
| Без анимации | `axis` и `travel` пишутся в `MechanismConfig` вручную |
| Составное движение, несколько узлов, сложная траектория | `Actuator.ANIM`: весь механизм это **одна** анимация `mech_<id>`, которая двигает сколько нужно узлов |

**`ANIM` и плеер.** Плеер ставить не надо, механизм его не запускает. При импорте `.glb` Godot сам создаёт `AnimationPlayer` с анимациями `mech_<id>` внутри инстанса модели. `C_Mechanisms` находит его по имени анимации, берёт её `Animation` и дорожки позиции, поворота и масштаба узлов, а `Mech.apply` ставит позы узлов по состоянию `t`: время между **первым и последним ключом** анимации (первый ключ не обязан стоять в нуле). Своих плееров механизм не заводит, несколько механизмов с разными анимациями двигаются одновременно и не мешают друг другу. Постоянные дорожки (ключи покоя без движения) пропускаются, дорожки костей и узлы, которых нет в модели, тоже (предупреждение в Output); если два механизма ведут один узел, предупреждение тоже. Время хода берёт `MechanismConfig.duration` (анимация растягивается), имя анимации `anim_name`, `part_role` у `ANIM` не нужен.

**Ось.** `axis` в `MechanismConfig` это ось в системе родителя; у дверей кузова это оси кузова (+X вправо, +Y вверх, -Z вперёд), знак у пары зеркальный. +Y Blender это -Z Godot.

**Id механизма** это часть имени действия `mech_<id>`. Он же хранится в свойстве `mech_id` объекта (Custom Properties, уходит в `extras`) и показывается в панели EC; у каждого механизма свой Id.

## 24.7. Свет

Источники света и свечение остаются в `LightConfig` ([ATTN_16](ATTN_16_mechanisms.md) §16.4), в модели света нет. Чтобы не подбирать числа на глаз, в Blender ставятся пустышки-якоря (`headlight_front`, `headlight_rear`, `cab_light`) с ролью, `glb_preflight.py --offset-y <offset_mesh_y>` печатает готовые `position` и `rotation_deg` в системе корня сцены модели. Числа копируются в `LightConfig`; сам якорь в игре не нужен. Светящиеся элементы модели (`emit_*`) подключаются через `glow_*` по роли узла.

## 24.8. Инструкции

Полный порядок с кнопками панели EC лежит в [`tools/blender/CHEATSHEET.md`](tools/blender/CHEATSHEET.md). Ниже суть.

### Подготовка модели в Blender

1. **Единицы и оси**: Metric, Unit Scale 1.0, нос +Y, центр кузова в нуле, Z=0 на оси буферов.
2. **Эталон** (панель EC, блок 2): два рельса-бокса 0.1 × 25 × 0.25 (внутренние грани на расстоянии колеи 1.65, верх на Z = −1.061) и колёсные пары (два колеса в центрах колеи и ось) заданного диаметра; в экспорт не входят. Колёса не должны проходить сквозь пол и стенки рамы.
3. **Кузов**: один меш с осмысленным именем. Подвижные части (двери, люки, пантограф, вентилятор): отдельные меши, дети кузова (Ctrl+P, Object (Keep Transform)).
4. **Origin детали**: для вращения на оси вращения (Set Origin, Origin to 3D Cursor).
5. **Роли**: панель EC, блок 1, или Custom Property `role` на объекте. «Удалить роль» снимает роль (и с данных меша, если она попала туда по ошибке). `buffer_1`...`buffer_4`: пустышки на осях буферов. **Ось буфера**: у пустышки её положение, у меша центр габарита (origin меша не учитывается). Если меш не симметричен (рассекатель снега) или буферов нет, кнопка «Создать пустышки буферов» ставит четыре на стандартные места (Z=0, шаг 1.74, торцы кузова).
6. **Материалы** по §24.5 (`paint_*`, остальные с префиксами), UV по §24.5.
7. **Механизм** (блок 3): «Ключ: покой» (кадр 0, действие получает имя `mech_<id>` и свойство `mech_id`), сдвинуть или повернуть деталь, «Ключ: рабочее» (кадр «Кадров хода» + 1), вернуть деталь. Одно движение на деталь (либо сдвиг, либо поворот), масштаб не анимируется, интерполяция Linear, канал без движения удаляется сам. Занятый Id отклоняется.
8. **Применить трансформы**: у кузова все, у частей только Rotation и Scale (Location не применять: он потерял бы origin шарнира).

### Экспорт

Панель EC, блок 4: проверка (при ERROR экспорт останавливается), `.glb` в `<Папка моделей>/<id>/<id>.glb`, затем проверка готового файла. Настройки экспорта проекта: +Y Up, Custom Properties включены, камеры и свет выключены, Apply Modifiers, UVs и Normals, **без Draco** (Godot его не читает), режим анимаций Actions (каждое действие отдельной анимацией), Always Sample Animations и Skinning выключены. При повторном экспорте имя файла то же: `uid` в `.import` сохраняется. В git идут `.glb` и `.glb.import`.

### Подключение в Godot

1. **Импорт.** Положить `.glb` в `res://data/models/<id>/`, дождаться импорта (параметры по умолчанию подходят).
2. **Сцена-обёртка** вместо копирования мешей:

```
WagonRigidBody3D (RigidBody3D)
├── <корень .glb, instance>      # кузов и вся иерархия частей, меши остаются в .glb
└── WagonCollisionShape3D        # BoxShape3D по числам отчёта
```

   `Make Local` и `Editable Children` на мешах не включать. Корень `.glb` становится `mesh_nodes[0]`, части находятся по ролям. Отладочных узлов и пустых `AnimationPlayer` в сцене нет.
3. **Паспорт.** `WagonConfig`: `coupler_offset` и коллизия из отчёта, `offset_mesh_y = WagonConfig.BUFFER_HEIGHT` для новых моделей, `mechanisms` (§24.6), `lights` (§24.7). Для `ANIM`: `actuator = ANIM`, `anim_name`.
4. **Проверить:** вагон на треке стоит буферами на той же высоте, что остальные; колёса на рельсе; двери открываются и закрываются по одной и все сразу; «Весь корпус» красит только `paint_*`.

## 24.9. Инструменты, отладка и проверка

**`tools/glb_preflight.py`** (Python, Godot не нужен): `python tools/glb_preflight.py <файл> [--kind wagon|loco|building] [--config <.tres>] [--offset-y N] [--buffer-h 1.061] [--tol 0.043] [--brush]`. Проверяет: один корень с `role=body`; уникальные роли `snake_case`; хвосты `.001`, пробелы, имена `Cube`/`Plane`, отладочные узлы; меши вне иерархии кузова; масштаб (ERROR) и поворот в покое; центр габарита; материалы (`paint_*`, прозрачность); UV0 и UV2; число треугольников; камеры, свет, скины; анимации (имя `mech_*`, канал, интерполяция, узел с ролью); высоту, шаг и нижнюю кромку буферов (роли `buffer_*`); ссылки конфига на роли модели. Печатает заготовки `MechanismConfig`, `LightConfig`, коллизию кузова, `coupler_offset`. `--offset-y` это `offset_mesh_y` (не задан: стандартная высота буферов, как у новой модели).

**Панель EC** (Blender 4.2 и новее, проверена на 5.0.1): вкладка EC в боковой панели 3D-окна.

| Блок | Что делает |
|---|---|
| Проверить модель | те же правила на объектах сцены; отчёт в панели (с переносом строк), в буфере обмена (копируется сам) и в тексте `EC_report`; кнопки «Показать» (окно без обрезки), «Копировать», «В Text» (окно с редактором Text) |
| 1. Роли | назначить из шаблона или своё имя, «Удалить роль», «Создать пустышки буферов» |
| 2. Подготовка | «Применить трансформы», «Создать UV1/UV2», «Убрать лишние UV», эталон рельсов и колёсных пар |
| 3. Механизм | активный объект, его действие и Id (Id следует за активным объектом, пипетка), ключи покоя и рабочего положения |
| 4. Экспорт | папка моделей, путь, экспорт и проверка готового файла (отчёт тоже копируется) |

Без интерфейса: `blender -b <файл>.blend -P tools/blender/ec_model_tools.py -- check` или `-- export --id <id>`; код возврата 1 при ERROR.

**Тесты (Godot, F6):** `tests/mech_anim_test.tscn` даёт `Mech anim: 12/12` (две анимации одновременно, ключи не с нуля, постоянные дорожки, конфликт узлов, контроль позы); `tests/library_paint_test.tscn` даёт `n/n` (среди проверок `paint_*`).

**Отладка механизмов.** `MechanismConfig.debug_log = true` печатает в Output привязку дорожек (узел, тип, ключи, пропущенные постоянные), каждую команду, остановку и сообщение «ПОЗА ИЗМЕНЕНА СНАРУЖИ» (поза неподвижного механизма изменилась, с указанием, кто в этот момент двигался). Во вкладке Debug у `ANIM` видны ведомые узлы и ошибка позы. Предупреждения без флага: узел ведут два механизма, анимация или узел не найдены.

**Типичные причины сбоев**

| Симптом | Причина |
|---|---|
| Деталь не двигается | нет `role` на объекте (роль на данных меша) или роль, имя анимации и конфиг не совпадают |
| Дверь едет не туда | ось в `MechanismConfig` в осях Godot: +Y Blender это -Z Godot |
| Вращение вокруг странной точки | origin не на оси вращения |
| Вагон выше или ниже остальных | ось буферов не на Z=0 или `offset_mesh_y` не 1.061 |
| «Весь корпус» красит сталь и резину | нет материалов `paint_*` |
| Кисть недоступна | нет UV2 (кисть работает только на меше кузова) |
| Деталь «уехала» после экспорта | Apply Location на детали сбросил origin |
| Ховер вагона только по крыше, не по боку | вагон на слое земли (слой по умолчанию у сцены); слой должен задавать код (п. 9 контракта) |
| Роль не доходит до игры | не включено Include, Custom Properties при экспорте, или роль на данных меша |

## 24.10. Управление (хоткеи)

Раздел добавил отладочные клавиши механизмов и света ([ATTN_16](ATTN_16_mechanisms.md)); остальные клавиши принадлежат другим разделам.

| Ввод | Когда работает | Что делает |
|---|---|---|
| **O** (`mechanisms_toggle`) | `Global.debug_mode`, вагон выбран | переключает все механизмы выбранного вагона |
| **I** (`lights_toggle`) | то же | свет выбранного вагона вкл/выкл |
| **Shift+I** (`mechanisms_gizmos`) | то же | метки источников света и размеры кузова в Output |
| Вкладка «Механизмы» в InfoPanel | вагон выбран | чекбокс и ползунок на механизм, «Открыть все», «Закрыть все» |

Blender: панель EC открывается клавишей **N** (вкладка EC); в работе используются штатные Ctrl+P (родитель), Ctrl+A (применить трансформы).

## 24.11. Организация папок

Каталог читает только `*.tres` из `data/<категория>/objects/`, без рекурсии, пути к ним записаны в сейвах; паспорт `data/library/info/<ключ>.tres` ищется по ключу. Эти места не меняются. Всё тяжёлое группируется по модели:

```
data/models/<id>/                      # по одной папке на модель
  <id>.glb (+ <id>.glb.import)         # экспорт из Blender, имя постоянное
  <id>.tscn                            # сцена-обёртка
  tex/                                 # внешние текстуры, если не вшиты
data/trains/objects/<id>.tres          # объект каталога
data/library/info/<ключ>.tres          # паспорт
```

Вид модели читается по id (`wagon_`, `loco_`, `house_`), подпапок по видам нет. Исходники `.blend` лежат вне репозитория (`E:\GodotCopy\Blender\Art\`). Переезд старой модели делается в панели FileSystem Godot (она переписывает `ext_resource` и держит `uid`), по одной модели за коммит. Старые папки (`data/import/`, `data/trains/*.tscn`) остаются, пока на них есть ссылки.

## 24.12. Ограничения и допущения

* Нос по +Y Blender выведен из математики экспортёра (+Y Blender -> -Z Godot), а то, что Godot не читает Draco, из документации Godot: оба пункта отдельной проверки в редакторе не имели.
* Допуск шага буферов в проверке вдвое шире NEM (±0.035 против ±0.017): у прототипов шаг 1750 мм.
* NEM 362 (посадочное место сцепки) в игре не моделируется.
* `ANIM` ведёт только позицию, поворот и масштаб узлов (без костей, без морфинга); время хода одно на механизм (`duration`).
* Кисть работает только на одном меше (кузов с UV2).
* Коллизия кузова строится вручную из чисел отчёта, из `.glb` автоматически не создаётся.
* Окно, буфер обмена и подписка на смену активного объекта в панели EC без графического окна не проверялись.
